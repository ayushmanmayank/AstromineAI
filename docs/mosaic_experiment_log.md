# Global-Mosaic Experiment Log

Working log for the global-mosaic dataset task (branch
`final/mosaic-dataset`), kept separate from `docs/month1_log.md` per
that task's explicit instruction not to modify the Month 1 logs or
results. This log is distilled into `docs/FINAL_REPORT.md`'s
"Global-mosaic experiment" section once all stages are complete (or
into a gate-failure report if a gate stops the experiment early).

Non-negotiable rules this experiment is held to throughout: no labels
from visual heuristics (labels come only from the VIR mosaic rasters);
label thresholds fixed and committed (`ml/data/mosaic_labels.py`) before
any model sees them; the test set touched exactly once, at the very
end; splits by large (>=20 deg) region blocks, never random tiles; any
failed gate stops the experiment and is reported as-is, with no accuracy
target promised or worked around.

### Real metadata, read directly from both formats (not assumed)

**FC** (`Vesta_Dawn_FC_HAMO_Mosaic_Global_74ppd.tif`, read via `rasterio`):
- Projection: Simple Cylindrical (Equirectangular), `central_meridian=0`,
  `standard_parallel_1=0`, on a 255000 m sphere (same body model VIR's
  label uses).
- Grid: 26704 x 13352 px, 8-bit (`uint8`), nodata=0.
- Resolution: 74.1778 px/degree (60.0 m/px) — confirmed via the embedded
  affine transform (`60.00, 0.00; 0.00, -60.00`).
- Longitude: real, documented (USGS map page) east-positive, domain
  -180..180, **already in the real Claudia-Double-Prime/SPICE frame** —
  this specific file was shifted +150 degrees eastward from the original
  Dawn-Claudia file specifically so that Claudia crater sits at 146E,
  matching the IAU-adopted frame. No further offset needed for this file.

**VIR** (4 self-labeled PDS3 `.IMG` rasters, read via a hand-written
binary reader, `ml/data/mosaic_reader.py` — matching this project's
existing PDS3-QUBE-reading convention rather than a new dependency):
- Projection: Equirectangular, planetocentric, positive-east,
  `CENTER_LATITUDE=0`, `CENTER_LONGITUDE=180` (label's own 0-360 scale).
- Grid: 16024 x 8012 px, 32-bit big-endian `IEEE_REAL` (confirmed
  empirically: big-endian gives physically sane 0.91-0.96 micron Band I
  center values and an exact match to the label's declared
  `MISSING_CONSTANT`; little-endian gives nonsense).
- Resolution: 44.505895925855 px/degree.
- Nodata: `MISSING_CONSTANT = -1.0E+32` (plus 4 sibling
  saturation-constant bit patterns the label also declares — handled
  with a tolerant `|value| > 1e30` catch-all in the reader, not just an
  exact-match check).
- Units: Band I/II **center** values are in microns (confirmed via the
  volume's own `CATALOG/VIR_DDR_VESTA_MOSAICS_DS.CAT`: band centers come
  from a parabola fit to the continuum-removed minimum, same technique
  — and same literature citation, De Sanctis et al. 2012 — this
  project's own `ml/data/spectral_labeling.py` already uses). Band I/II
  **depth** values are the unitless Clark & Roush (1984) `1 - Rc/Rb`
  fraction — again the exact same definition this project's own
  `compute_band_depth()` already implements, independently confirmed
  from the catalog text, not assumed to match.
- **Longitude offset, real and documented, not assumed**: the same
  catalog file states explicitly: *"The maps are centered at latitude
  0.0 and longitude 330.0 in the IAU-compliant Claudia double prime
  system. This corresponds to 180.0 longitude in the system used in
  publications."* Since the label's own `CENTER_LONGITUDE=180` matches
  the "publications" value, every longitude in this label's own scale is
  offset from the real Claudia-Double-Prime/SPICE frame (the same frame
  FC's file natively uses) by **label_lon = (claudia_lon − 150) mod
  360**.

### The empirical longitude cross-check (GATE A step 3)

Real reference coordinates (IAU/USGS gazetteer, same convention this
project's own Slice 11 already used for Rheasilvia):
`Rheasilvia 86.300E, -71.950`; `Divalia Fossae 196.233E, -9.050`.

FC's own pixel conversion needed no sign resolution (its CRS's
`central_meridian=0` already *is* the documented Claudia-Double-Prime
meridian) — cropping both reference points produced real, visibly
crater-textured Vesta terrain (not blank/garbage), confirming the FC
conversion works.

VIR's label-to-pixel sign (PDS3 leaves `POSITIVE_LONGITUDE_DIRECTION=EAST`
equirectangular's sample-vs-longitude sign implementation-defined) was
resolved empirically against Rheasilvia's real, literature-documented
diogenite-rich signature (De Sanctis et al. 2012 — shorter Band I
wavelength — same citation Slice 11 used): **a real mistake was made and
caught here**. An initial check tested both candidate signs *without*
first applying the real +(-150) degree Claudia offset, found `lon_sign=+1`
to be the apparent match, and nearly locked that in. Re-running with the
offset correctly applied first (the sign and offset are not independent —
a 150-degree shift moves the sampled pixel column by nearly half the
image width) **flipped the result**:

| lon_sign (offset applied first) | local Band I center mean | vs. real global mean (0.92650, std 0.00270) | verdict |
|---|---|---|---|
| +1 | 0.92705 | +0.206 std | no significant deviation |
| **-1** | **0.92499** | **-0.559 std** | **matches the documented diogenite (shorter-wavelength) signature** |

**`lon_sign=-1` is confirmed correct** and is the only option
`ml.data.mosaic_reader.vir_lonlat_to_pixel()` implements (not left as a
runtime parameter, to prevent this exact mistake from recurring
silently). Side-by-side real crops saved to
`datasets/mosaic/checks/{Rheasilvia,Divalia_Fossae}_fc_vs_vir_confirmed.png`.
VIR's crops show real but visually noisy/blocky structure (orbital-swath
seam artifacts) rather than a clean crater silhouette — expected, since
Band I center measures *composition*, not albedo/shading, and real
sub-percent-level inter-swath noise is amplified by percentile-based
display contrast stretching; this is why the literature-grounded
quantitative check (not a visual-only check) was the decisive evidence.

## Stage 2: Labels (GATE B)

### Step 2: fixed, committed thresholds

Checked directly before deciding (not assumed to transfer): this
project's existing pointwise literature thresholds
(`ml/data/spectral_labeling.py`'s `BAND_I_THRESHOLDS_UM`, 0.92/0.95 —
diogenite/howardite/eucrite-like) produce a **completely degenerate
split** on this global, multi-phase-averaged mosaic: 1.14% / 98.86% /
0.00% of all real valid pixels (n=99,477,029) — essentially the entire
planet falls in the single "howardite_like" bucket under those
thresholds. This is itself a real, reportable finding (the global
mosaic's real Band I center dynamic range, 0.9102-0.9598 μm, is far
narrower than individual calibrated-spectrum extractions show).

**Used tertiles of this mosaic's own real distribution instead** (fixed
and committed in `ml/data/mosaic_labels.py` *before* any model saw them):
cut points **0.925423 μm** and **0.927530 μm**, giving real class
fractions `band1_low` 33.25%, `band1_mid` 33.39%, `band1_high` 33.36% —
genuinely balanced. Class names deliberately neutral (not
diogenite/howardite/eucrite), so these are never mistaken for the
validated pointwise scheme used elsewhere in this project.

## Stage 3: Tiles + split

Real, fixed rules (`scripts/mosaic_tile.py`, not tuned after seeing
results): 224x224 px tiles at FC's native resolution (3.0198°/side, one
scale — a second scale is a documented future option, not pursued here
given time scope); drop a tile if >20% of its real FC pixels are
nodata; label = majority real VIR tertile class within the tile's real
footprint (both mosaics are true equirectangular on the same sphere, so
a rectangular FC tile maps to an exact rectangular VIR-pixel window —
only 2 corners need converting per tile, not every pixel); drop a tile
if <60% of its covering VIR label pixels agree (a real majority with
margin, not a bare ~34% plurality). Region-block (20°) split with a
one-tile buffer (`ml/utils/mosaic_splits.py`).

**Real result**: of 7021 candidate tiles, 2975 kept. Dropped: 0 for
nodata (FC's real coverage has no gaps at this scale), 869 for no real
VIR coverage overlap at all, **3177 for low label purity** — more than
45% of all candidate tiles. This is itself an important, honest finding:
the tertile classes are finely spatially intermixed within individual
~3°-wide tiles far more often than they form clean, tile-sized regional
blocks — consistent with Stage 2's narrow real dynamic range finding
(0.9102-0.9598 μm across the whole planet). A further 1481 tiles were
buffered out near block boundaries, leaving **1494 real tiles** across
the three splits:

| split | total | band1_low | band1_mid | band1_high |
|---|---|---|---|---|
| train | 1049 | 455 | 133 | 461 |
| val | 223 | 55 | 35 | 133 |
| test | 222 | 96 | 27 | 99 |

Two real, honest characteristics of this split, reported plainly rather
than smoothed over:
1. **`band1_mid` is underrepresented in every split** (13-16% of each,
   vs. ~33% at the pixel level) — majority-voting many pixels per tile
   systematically favors the two extreme tertiles over the narrow
   middle one, a real statistical consequence of tile-level aggregation
   of a 3-way split, not a bug.
2. **Class balance differs noticeably across splits** (`band1_high` is
   60% of val but only 44%/45% of train/test) — a real, expected
   consequence of region-BLOCK (not tile, not i.i.d.) splitting: whole
   large geographic blocks are assigned to a split as a unit, so if
   `band1_high` happens to concentrate in the particular large regions
   that were randomly assigned to val, val's class balance shifts
   accordingly. This is accepted as the honest cost of leakage-safe
   spatial splitting, not corrected post-hoc (stratifying splits by
   label at the block level would require choosing blocks based on
   their own label content, which risks exactly the kind of label-aware
   split-selection this experiment's rules are designed to prevent).

Real tile manifest (committed): `datasets/mosaic/manifests/tile_manifest.csv`
(2975 rows — every candidate tile that survived nodata+purity filtering,
including the 1481 marked `split=buffered_out`, so the full real
accounting is traceable). Tile PNGs themselves are *not* committed
(`datasets/mosaic/tiles/`, gitignored, regenerable from the manifest +
the checksummed raw mosaics). Spot-checked: real tile images show
genuine Vesta crater-field terrain, not corrupted/blank data.

## Stage 5: FINAL — real test set, touched exactly once (`scripts/mosaic_evaluate_test.py`)

**What these labels measure, stated plainly one more time before any
number below**: Band I (pyroxene absorption) center-wavelength TERTILE
bins of the real VIR global mosaic (`ml/data/mosaic_labels.py`). **Not
a validated mineral-composition classification** — see Stage 2's
finding that the project's existing literature pointwise thresholds
(diogenite/howardite/eucrite, 0.92/0.95 µm) produce a degenerate split
on this raster and were deliberately not reused here.

Test touched for the first and only time in this script, on the real
222-tile Stage-3 test split (`band1_low`=96, `band1_mid`=27,
`band1_high`=99; majority-class rate = 99/222 = **44.59%**). Stage 2's
confound screen (Gate B) used a separate, coarser pixel-level sample
(every 20th valid VIR pixel, its own independent region-block split)
purely as a pre-modeling diagnostic — it never informed any choice
evaluated below, but for full transparency: because `assign_block_splits`
shuffles whatever list of unique blocks it is handed, and Stage 2 and
Stage 3 hand it different underlying point sets, Gate B's "test" blocks
are not guaranteed to be the identical real blocks as Stage 3's — they
are two independently-derived splits, not one split reused twice.

The trivial baseline is **refit here**, on real tile-level features
(each test/train tile's own mean FC pixel value as "albedo", plus its
real center lat/lon), so it is evaluated on the *identical* real test
tiles as the deep models — a fair, apples-to-apples comparison, rather
than reusing Gate B's differently-sampled numbers.

| model | n | accuracy | balanced accuracy | macro-F1 | ECE |
|---|---|---|---|---|---|
| Trivial baseline (RF: albedo + lat/lon, refit on tiles) | 222 | **0.7162** | **0.5530** | **0.5374** | 0.1190 |
| ResNet-50 (class-weighted) | 222 | 0.5180 | 0.5067 | 0.4744 | 0.0765 |
| ViT-B (baseline) | 222 | 0.6261 | 0.4831 | 0.4636 | 0.0791 |
| Ensemble (averaged softmax) | 222 | 0.6216 | 0.5056 | 0.5072 | 0.0700 |

Confusion matrices (rows=true, cols=predicted, class order
`[band1_low, band1_mid, band1_high]`):

- Trivial baseline: `[[82, 2, 12], [1, 1, 25], [16, 7, 76]]`
- ResNet-50 (class-weighted): `[[26, 11, 59], [4, 13, 10], [13, 10, 76]]`
- ViT-B (baseline): `[[58, 0, 38], [17, 1, 9], [18, 1, 80]]`
- Ensemble: `[[48, 2, 46], [11, 4, 12], [13, 0, 86]]`

**Real, honest finding, stated plainly and not worked around**: on the
real held-out test set, **no deep model beats the real trivial
baseline on balanced accuracy or macro-F1** — the metrics this task
asks for specifically because raw accuracy rewards majority-class
guessing. The class-weighted ResNet-50's real Stage-4 *validation* gain
over Gate B's trivial baseline (val_bal_acc 0.5087 vs. 0.5580, still
behind at that point too, by a smaller margin) did **not** carry over
to test in a way that surpasses a same-tile trivial baseline
(0.5067 vs. 0.5530). The ensemble's balanced accuracy (0.5056) and
macro-F1 (0.5072) are close to the trivial baseline's but still
slightly below it on both. Raw accuracy alone would have been
misleading here: ViT-B's 0.6261 accuracy looks like the second-best
number in the table, but its balanced accuracy (0.4831) is the
*worst* of the four, driven by predicting `band1_mid` almost never (1
of 27 correct) — exactly the majority-class-dominated failure mode
this task's "always report balanced accuracy/macro-F1 alongside raw
accuracy" rule exists to catch.

**Conclusion for this dataset, at this real training budget**: the
deep models learn to separate these VIR Band I tertile classes using
the FC image tiles about as well as a simple brightness + location
statistic already does, and on the real test set, not quite as well.
This is consistent with, and strengthens, this project's overall
cross-track finding (Slice 16, month1-data-pipeline) that apparent
spectral-cluster signal in this kind of data needs to be checked
against simple confounds before being called a model achievement.

**Honest visual assessment**: in every one of the 6 tiles, the Grad-CAM
heatmap's brightest region sits directly on the same bright
curved ridge / albedo-edge feature that is visually the most prominent
brightness transition in the raw FC tile (a crater-rim-like bright
crescent against darker terrain) — not on some other, independently
compositional-looking structure. This is consistent with Grad-CAM
tracking real brightness/shading edges in the input rather than an
independent compositional signal, which is exactly the kind of confound
this whole project (both tracks) has repeatedly found and reported
rather than assumed away. The ViT-B attention rollout maps are diffuse
and dominated by a small number of isolated, often corner- or
edge-biased patches with no visible structured relationship to the
bright ridge feature Grad-CAM and the raw image agree on — consistent
with the ViT-B underperformance and the Month 2 engineering track's own
documented attention/mode-collapse concerns for this architecture, and
providing no basis here for claiming the ViT-B arm is attending to
compositional structure either.
